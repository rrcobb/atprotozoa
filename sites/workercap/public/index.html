799 Workers,
500 allowed.

This repository has 803 small sites. A Cloudflare account can have a maximum of 500 Workers. This page has seven steps. The steps show the setup before the change, the problem, the solution, and the setup after the change.

Step 1 · the limit

One account can have 500 Workers.

A Worker is one script that runs on Cloudflare. The Workers Paid plan limits an account to 500 Workers. Cloudflare counts a Worker that serves static files in the same way as a Worker that runs code.

Step 2 · before the change

Each site had its own Worker.

Each folder in sites/ had a wrangler.toml file. Each deploy made a Worker with the name atprotozoa-<site>. Each Worker had a route for the hostname of its site. The Worker sent each request to a set of static files.

Most of those Workers had the same ten lines of code. The code sends the request to the set of files. 592 sites needed no other function.

Step 3 · the problem

The account had 799 Workers.

Above 500, the existing Workers continue to serve and deploy. A request to create a new Worker fails with this error:

You have exceeded the limit of 500 Workers
on your account. [code: 10037]
  1. 2026-08-20 — the account goes above 500 Workers. Deploys continue to work. Newer wrangler versions use an upload path that does not do the check.
  2. 2026-09-17 — a request to increase the limit goes to Cloudflare. Cloudflare does not answer. For more than 500 Workers, Cloudflare recommends Workers for Platforms.
  3. 2026-10-29 — strandbeest is the last new Worker.
  4. 2026-10-31 — the upload path returns error 10037. Nine new sites cannot deploy.
Step 4 · the solution

One Worker can do the same job for many sites.

The fallback Worker already had the wildcard route *.bisks.net/*. It reads the hostname. It finds the folder for that hostname. It sends the files from that folder. A site with no server code needs a folder. It does not need a Worker.

Each hosted site keeps its own hostname. Thus each site keeps its own origin, cookies, localStorage, and OAuth login.

Step 5 · the migration

Four actions for each site. Each action has a check.

  1. classify — migrate-to-host.mjs finds sites where the Worker only sends requests to the set of files. A site with a binding, a cron trigger, or custom code keeps its Worker.
  2. host — delete the wrangler.toml file and the src/ folder of the site. Add the site to fallback/sites.json. Push the change. The fallback Worker deploys with the site files.
  3. cut over — cf-cutover.mjs --routes removes the old route. It waits until the fallback Worker answers. It compares the status code and a hash of /. If they are different, it restores the route.
  4. delete — cf-cutover.mjs --workers deletes the old Worker. This makes one Worker available again. The script deletes Workers with a Custom Domain one at a time. The deletion also deletes the DNS record.
Step 6 · after the change

Four host Workers (atprotozoa-host-1 to -4) split the hosted sites into groups of 148 sites. A push to one site deploys only its group of 148 sites. The other 444 sites do not change.

Step 7 · other limits

Two other limits apply to the zone.

The zone has two more limits. Each limit stopped deploys before the Worker limit did.

A new site today is a folder with public/ and site.json. The wildcard route covers it. It uses no Worker and no route. A site with server code uses one Worker and one route.
